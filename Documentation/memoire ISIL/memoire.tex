\section*{English}
The rapid expansion of digital healthcare services necessitates infrastructure that reconciles high availability with operational cost-efficiency. Traditional manual resource allocation fails to respond to the dynamic volatility of high-load web applications. This thesis proposes an autonomous hierarchical framework for intelligent resource provisioning. The architecture integrates a hybrid meta-heuristic algorithm, combining Whale Optimisation (WOA) and Differential Evolution (DE), to optimize virtual machine placement across physical nodes. The solution is validated through the deployment of a distributed medical information system, demonstrating proactive scalability and resilient fault domain isolation.

\chapter*{General Introduction}
\addcontentsline{toc}{chapter}{General Introduction}

The global transition toward digitized healthcare systems has imposed unprecedented demands on the resilience and scalability of IT infrastructures. Modern medical information systems must sustain continuous availability while processing high volumes of sensitive data under volatile traffic patterns. Traditional infrastructure management, characterized by static provisioning and manual oversight, proves insufficient for these high-load environments. The latency associated with human intervention and the inefficiencies of rigid resource allocation often lead to service degradation or excessive capital expenditure.

Achieving a balance between hardware efficiency and service continuity presents a structural tension. Dense workload placement maximizes utilization but increases the risk associated with physical node failures. Conversely, over-provisioning ensures a safety margin but results in significant underutilization of hardware assets. This thesis addresses this problem by proposing an autonomous provisioning framework that utilizes intelligent scheduling and predictive remediation.

The objective of this research is the design and implementation of a self-regulating cluster architecture capable of managing microservices at scale. By leveraging meta-heuristic optimization for virtual machine placement and risk-stratified cognitive agents for orchestration, the system provides a robust solution for deploying complex web applications. The study is organized into three distinct phases: a review of current abstraction technologies, the theoretical architectural design, and the concrete implementation of a distributed medical information system.

\chapter{Conception}

\section{Introduction}

This chapter delineates the theoretical and architectural design of the autonomous cluster management system. The design is technology-agnostic, presenting a generalized model for resilient infrastructure that satisfies the requirements of high-load web applications. It defines the hierarchical layers, the mathematical optimization heuristics, and the cognitive agent logic required for self-regulation.

\section{Design Objectives and Validation Criteria}

The primary objective is the resolution of the structural tension between resource efficiency and service availability. The system must maintain high node density while ensuring performance isolation and headroom for traffic surges. The proposed architecture is validated through four criteria: automated provisioning latency, responsive remediation of resource contention, constraint-respecting scheduling, and the preservation of continuous availability during failure events.

\section{Layered Infrastructure Architecture}

The infrastructure is conceptualized as a four-layer hierarchical stack. Each layer provides abstracted services to the layer above. The Physical Layer provides hardware capacity. The Virtualization Layer manage hardware abstraction into virtual machines. The Containerization Layer hosts microservice workloads. Finally, the Monitoring Layer observes telemetry to drive orchestration logic.

\section{Physical and Network Foundation}

The foundation rests on failure domain isolation, where hardware is segmented to prevent single points of failure. The network architecture implements a three-segment isolation model:
\begin{itemize}
    \item \textbf{Workload Segments:} Isolated environments for distinct microservice groups.
    \item \textbf{Observability Segment:} A dedicated segment for telemetry and administrative traffic.
    \item \textbf{Management Segment:} Restricted access for orchestration agents.
\end{itemize}

Routing follows a default-deny posture, where inter-segment communication requires explicit authorization policies.

\section{Virtualization and VM Placement}

\subsection{Mini-Cluster Partitioning}
To optimize scheduling, the virtual fleet is logically partitioned into mini-clusters. This strategy confines the search space of placement algorithms, reducing computational complexity while ensuring microservice co-location for high-frequency communication patterns.

\subsection{Hybrid WOA-DE Placement Algorithm}
The mapping of Virtual Machines to Physical Hosts is determined by a hybrid algorithm combining Whale Optimisation (WOA) and Differential Evolution (DE). This combination ensures both robust global exploration and precise local exploitation.

\begin{algorithm}[H]
\DontPrintSemicolon
\KwIn{VM Request $\vec{R}$, Host Metrics $M$, Population $N$}
\KwOut{Optimal Mapping $H^*$}
Initialise population of candidate host assignments\;
\While{Termination criteria not met}{
    Evaluate Fitness $f(X)$ using weighted Euclidean distance\;
    \tcp{WOA Update Phase}
    Update positions via shrinking encirclement and spiral movement\;
    \tcp{DE Update Phase}
    Apply mutation and crossover to maintain population diversity\;
    Select survivors through tournament selection\;
    Update global best $H^*$\;
}
\Return $H^*$\;
\caption{Hybrid WOA-DE Provisioning Algorithm}
\label{alg:woa_de}
\end{algorithm}

\subsection{Fitness Function}
Placement quality is evaluated using a multi-objective weighted Euclidean distance formula. The objective is to minimize the resource differential between the request and the host's available capacity.

\begin{equation}
\text{Fitness} = \sqrt{w_C (\Delta C)^2 + w_R (\Delta R)^2 + w_I (\Delta I)^2 + w_E (\Delta E)^2}
\end{equation}

Where $\Delta C, \Delta R, \Delta I, \Delta E$ represent standardized Z-scores for CPU, RAM, I/O, and Energy respectively, subject to $\sum w_i = 1$.

\subsection{Virtualization}

Virtualization enables the creation of simulated computing environments abstracted
from physical hardware. A hypervisor partitions physical resources into isolated
virtual machines (VMs), each with its own allocated CPU, memory, storage, and
network interfaces \cite{popek1974formal}. By decoupling software execution from
hardware, multiple operating systems can coexist on a single server while remaining
operationally independent \cite{rosenblum2005virtual}.

Key advantages include resource consolidation, reduced infrastructure costs, live
migration of running VMs between hosts, rapid provisioning of environments, and
flexible workload placement \cite{vmware2006consolidation, barham2003xen}.

\subsection{Containerization}

Containerization is a lightweight alternative that operates at the operating-system
level rather than the hardware level. Containers encapsulate application code with
its dependencies into portable units that share the host OS kernel, using kernel
features such as \textit{namespaces} for isolation and \textit{control groups} for
resource limiting \cite{merkel2014docker, soltesz2007container}.

Key advantages include faster startup times, higher deployment density, consistent
behavior across environments, natural alignment with microservices and CI/CD
pipelines, and declarative version-controlled definitions that simplify rollbacks
\cite{bernstein2014containers, pahl2015containerization}.

\section{Virtualized and Containerized Environments}
% ================================================================

\subsection{Virtual Machine Architecture}

Hypervisors come in two types: Type~1 (bare-metal) run directly on hardware, while
Type~2 run atop a host OS \cite{rosenblum2005virtual}. Each VM includes a full
guest OS and virtualized hardware managed by the hypervisor, providing strong
isolation at the cost of higher resource overhead and longer boot times
\cite{barham2003xen}.

\subsection{Container-Based Environments}

Container runtimes such as Docker or containerd interface with the host kernel to
create isolated execution contexts. Namespaces prevent containers from observing
processes outside their scope; control groups prevent resource monopolization; and
union file systems allow containers to share common base layers while maintaining
isolated writable layers \cite{merkel2014docker, soltesz2007container}.

Container orchestration platforms such as Kubernetes add automated scheduling,
service discovery, health monitoring, and rolling updates to manage containers at
scale \cite{burns2016borg}.

\section{Microservices Architecture}
% ================================================================

\subsection{Definition and Principles}

Microservices structures applications as collections of loosely coupled,
independently deployable services, each implementing a specific business capability
and owning its own data store \cite{newman2015microservices}. Core principles
include single responsibility, bounded contexts from domain-driven design,
lightweight communication via HTTP APIs or message queues, decentralized governance,
and built-in resilience patterns such as circuit breakers and timeouts
\cite{fowler2014microservices, richardson2018microservices}.

\subsection{Benefits and Challenges}

Microservices enable independent deployability, technology heterogeneity, granular
scalability, team autonomy, and incremental modernization of legacy systems
\cite{newman2015microservices, fowler2014microservices}.

However, they introduce significant complexity: distributed debugging requires
sophisticated monitoring and tracing; cross-service transactions demand eventual
consistency models; network latency introduces new failure points; and substantial
operational infrastructure --- service discovery, load balancing, orchestration ---
becomes necessary \cite{richardson2018microservices}.

% ================================================================
\section{Microservices versus Monolithic Architecture}
% ================================================================

Monolithic architecture integrates all components --- UI, business logic, and data
access --- into a single codebase sharing a common database, deployed as one unit
\cite{fowler2014microservices}. Components communicate through in-process calls,
simplifying initial development and ensuring strong data consistency.

The key structural differences are summarized as follows. Monoliths exhibit tight
coupling where changes ripple across the codebase, while microservices enforce loose
coupling through stable interfaces. Monoliths use a shared database with strong
consistency; microservices use per-service databases, complicating cross-service
transactions. Monoliths scale by replicating the entire application; microservices
enable selective scaling of individual components. Failures in a monolith can
cascade system-wide, whereas microservices contain failures within service
boundaries --- though distributed failures introduce new failure modes
\cite{newman2015microservices, richardson2018microservices, fowler2014microservices}.

% ================================================================
\section{Critical Analysis: The Imperative for Microservices with Containerization
and Virtualization}
% ================================================================

\subsection{Limitations of Traditional Deployment}

Traditional deployment on physical or dedicated virtual servers suffers from
documented inefficiencies. Infrastructure often operates below 20--30 percent
average utilization while being over-provisioned for peak loads, representing
substantial capital waste \cite{vmware2006consolidation}. Manual provisioning is
slow and inconsistent, limiting organizational responsiveness. Environmental
discrepancies between development and production cause deployment failures
\cite{merkel2014docker}, and monolithic architectures offer limited fault tolerance
\cite{rosenblum2005virtual}.

\subsection{Should Organizations Transition to Microservices and
Virtualization/Containerization Environments?}

The strategic question is straightforward to pose but difficult to answer:
\textit{should organizations transition to microservices supported by virtualization
and containerization?}

The case for transition is clear in principle. Containerization delivers consistency
and resource efficiency; virtualization enables consolidation; microservices unlock
deployment velocity and team autonomy \cite{merkel2014docker, richardson2018microservices}.
Yet the associated costs are substantial. Container orchestration demands specialized
expertise, migration requires significant investment in infrastructure and personnel,
and the operational maturity required for distributed microservices exceeds what most
organizations have built through traditional models \cite{burns2016borg, bernstein2014containers}.

The decision is further complicated by inherent contradictions: larger organizations
may benefit most from consolidation yet face more complex migrations; stable legacy
systems may gain little from disruption; and containerization without architectural
transformation yields limited benefits, while microservices without containerization
introduce different operational burdens. Organizations must determine not only
\textit{whether} to adopt these technologies but \textit{in what sequence and scope}
--- questions for which industry guidance remains conflicting and empirical evidence
limited \cite{barham2003xen}.

\section{Introduction}
\label{sec:ch2_intro}

This chapter presents the full architectural design of a cluster infrastructure for
a high-demand web application, organised around three pillars: a proof of concept
defining clear validation criteria before any large-scale deployment, a four-layer
infrastructure stack from physical hardware to a monitoring plane, and an intelligence
and security layer combining a natural-language assistant, a predictive model, and a
zero-trust security design. The three pillars are mutually dependent: the monitoring
layer feeds the placement algorithm, the security layer protects that data, and the
predictive model learns from monitoring history.

\section{Proof of Concept: Goals and Validation}
\label{sec:poc}
% ================================================================

\subsection{Design Objectives}
\label{subsec:poc_objectives}

The system faces two requirements that pull in opposite directions:
\textit{resource efficiency} --- packing workloads tightly to maximise hardware
utilisation --- and \textit{continuous availability} --- keeping every service
reachable despite hardware failures or traffic spikes. The architecture resolves
this tension through intelligent scheduling and scaling that adapts in real time.
The application is built as loosely coupled microservices so that each service scales
independently and a fault in one causes graceful degradation rather than a full
outage \cite{newman2015microservices}.

\subsection{Validation Criteria}
\label{subsec:poc_criteria}

A time-bounded proof-of-concept phase verifies that all core mechanisms work together
before full-scale deployment. All four conditions must hold simultaneously:

\begin{itemize}
    \item \textbf{Automated provisioning:} a new VM joins the cluster automatically,
    within a defined time bound, with no manual steps.
    \item \textbf{Responsive scaling:} injected anomalies (CPU saturation, memory
    pressure, high error rates, packet loss) trigger the correct remediation within
    one monitoring cycle.
    \item \textbf{Constraint-respecting scheduling:} containers are placed without
    exceeding VM resource limits and rebalance automatically when VMs change.
    \item \textbf{Preserved availability:} the application remains reachable
    throughout all provisioning, scaling, and rebalancing operations.
\end{itemize}

\paragraph{Initial Sizing and Mini-Cluster Organisation.}
Each new VM receives an initial resource allocation derived from a workload profile
--- benchmarks, service-level objectives, or historical data from similar services.
A set of standard \textbf{size classes} is defined on top of this baseline, providing
pre-validated resource ratios for the most common workload types and simplifying
provisioning decisions for well-characterised services.
The monitoring layer tracks usage continuously and triggers vertical scaling if
sustained demand exceeds the initial allocation.

The VM fleet is partitioned into $k$ logical \textit{mini-clusters}, each grouping
VMs whose workloads communicate frequently. This reduces scheduling scope from $n$
physical machines to $n/k$ per decision (a factor-$k$ complexity reduction), keeps
related traffic local, and prevents hotspots \cite{zhang2020intelligent}.
Figure~\ref{fig:mini_clusters} illustrates the partitioning. The value of $k$ is
either set statically by the application designer, or inferred dynamically by a
machine learning model observing inter-service communication at runtime.

\paragraph{Provisioning Algorithm and Fitness Evaluation.}
VM placement uses a hybrid of the Whale Optimisation Algorithm (WOA)
\cite{mirjalili2016woa} and Differential Evolution (DE) \cite{storn1997de}.
At each iteration the candidate population is split into two disjoint subsets.
The \textbf{WOA subset} applies encirclement, spiral, or random-agent position
updates; the \textbf{DE subset} applies mutation, crossover, and greedy selection.
The global best $X^*$ is refreshed after both subsets. This prevents premature
convergence (a weakness of pure WOA) and the aimless drift that arises in DE when
population diversity collapses.

The fitness function scores a candidate host against the VM's request across four
dimensions (Table~\ref{tab:fitness_dims}). Each metric is first z-score normalised:

\begin{equation}
    X_i^{*} = \frac{X_i - \bar{X}}{\sigma_X}
    \label{eq:zscore}
\end{equation}

and combined into a weighted Euclidean distance:

\begin{equation}
    \text{fitness} = \sqrt{\,w_1(\Delta C)^2 + w_2(\Delta R)^2
        + w_3(\Delta IO)^2 + w_4(\Delta E)^2},\quad \textstyle\sum w_i = 1
    \label{eq:fitness}
\end{equation}

where $\Delta X$ is the gap between what the VM requests and what the host offers.
A lower score indicates a better placement.

\begin{table}[H]
    \centering
    \caption{Fitness Function Resource Dimensions}
    \label{tab:fitness_dims}
    \renewcommand{\arraystretch}{1.4}
    \begin{tabular}{|l|l|l|l|}
        \hline
        \textbf{Dimension} & \textbf{Symbol} & \textbf{Unit} & \textbf{Rationale} \\
        \hline\hline
        CPU Capacity   & $C$  & vCores & Prevents compute starvation \\
        \hline
        RAM            & $R$  & GB     & Avoids memory-induced swapping \\
        \hline
        I/O Throughput & $IO$ & MB/s   & Guards storage and network bandwidth \\
        \hline
        Energy Draw    & $E$  & J/hr   & Minimises operational energy cost \\
        \hline
    \end{tabular}
\end{table}

The full iterative procedure is shown in Figure~\ref{fig:woa_de} and summarised
below.

\textit{Initialisation.} Sample $n$ random VM-to-host mappings; set $X^*$ to the
lowest-fitness candidate; set $a_0{=}2$, scaling factor $F$, crossover rate
$CR{=}0.5$.

\textit{Main loop} (for $t = 0,\ldots,T-1$):

\begin{enumerate}
    \item \textbf{Parameter update.}
    \begin{equation}
        a = 2\!\left(1-\tfrac{t}{T}\right),\quad
        A = 2ar_1 - a,\quad C = 2r_2,\quad p\sim\mathrm{U}(0,1)
        \label{eq:woa_params}
    \end{equation}

    \item \textbf{WOA update} (for each $X_i$ in WOA subset):
    \begin{equation}
        X_i(t{+}1) =
        \begin{cases}
            X^* - A\cdot|CX^* - X_i|
                & p < 0.5,\;|A| < 1\;\text{(exploitation)}\\[4pt]
            X_{\mathrm{rand}} - A\cdot|CX_{\mathrm{rand}} - X_i|
                & p < 0.5,\;|A| \ge 1\;\text{(exploration)}\\[4pt]
            |X^*-X_i|\cdot e^{bl}\cos(2\pi l)+X^*
                & p \ge 0.5\;\text{(spiral)}
        \end{cases}
        \label{eq:woa_update}
    \end{equation}
    Refresh $X^*$ from the WOA subset.

    \item \textbf{DE update} (for each $X_j$ in DE subset):
    \begin{align}
        V_j   &= X^* + F\,(X_{r_1} - X_{r_2})
            \label{eq:de_mut}\\[2pt]
        U_j[k]&= \begin{cases}V_j[k]&\mathrm{rand}()\le CR\\
                              X_j[k]&\text{otherwise}\end{cases}
            \label{eq:de_cx}\\[2pt]
        X_j   &\leftarrow U_j\;\text{ if }f(U_j)<f(X_j)
            \label{eq:de_sel}
    \end{align}
    Refresh $X^*$ from both subsets.
\end{enumerate}

\textit{Output}: $X^*$ --- the recommended VM-to-host placement for the mini-cluster.

% --- NEW: Algorithm properties and limitations ---
The hybrid design exhibits five desirable properties.
(i)~\textbf{Dual exploration:} WOA spiral and random-agent modes explore the
solution space from directions anchored to $X^*$ and to random population members,
while DE mutation explores directions defined by the algebraic difference
$X_{r_1}-X_{r_2}$; the two mechanisms are geometrically independent.
(ii)~\textbf{Preservation of the global best:} both WOA contraction and DE
base-vector choice orient the population toward $X^*$, which is refreshed after
each phase so that improvements found during the WOA phase immediately influence
the DE phase.
(iii)~\textbf{Greedy selection:} DE discards any trial mapping that does not
improve upon its parent, ensuring monotonically non-increasing population fitness
across iterations.
(iv)~\textbf{Parameter sensitivity reduction:} mixing both paradigms distributes
the optimisation workload across two parameter sets whose failure modes are
uncorrelated.
(v)~\textbf{Suitability for discrete placement spaces:} the fitness function
handles the required continuous-to-discrete decoding, so both update rules apply
without modification.
The principal limitations are the O($n$) fitness evaluations per iteration, which
becomes significant at large fleet sizes, and the discrete decoding step required
before each evaluation.
% --- END NEW ---

\paragraph{Virtual Network Architecture.}
An overlay network decouples logical topology from physical cabling, enforcing
segment boundaries in software on each hypervisor node without reconfiguring
physical equipment. This approach provides greater flexibility and portability than
VLAN-based segmentation, and is particularly suited to environments where the
underlying infrastructure cannot be modified.
Three logical segments are defined: primary tenant workloads, a second isolated
environment (e.g.\ staging), and a dedicated monitoring segment. All inter-segment
traffic routes through a central virtual router enforcing \textit{default-deny}:
unmatched packets are silently dropped and cross-segment flows require explicit
bidirectional rules. The monitoring segment has targeted read-only access to other
segments; no reverse flow is permitted. An internal name-resolution service
eliminates reliance on external public resolvers, removing the DNS-redirection risk.

% ----------------------------------------------------------------
\subsection{Container Scheduling and Placement}
\label{subsec:containers}
% ----------------------------------------------------------------

Each microservice runs in its own container, isolated by kernel namespaces and
control groups. Containers are assigned to VMs using a \textbf{Best Fit} strategy:
the scheduler selects the VM with the least remaining capacity that can still meet
the container's requirements, filling VMs before touching less-loaded ones. This
minimises the number of active VMs and therefore total energy and licensing costs
\cite{coffman1984bin}. Mini-cluster boundaries are respected: containers from the
same mini-cluster are preferentially co-located on VMs in that mini-cluster to
preserve network locality.

% ----------------------------------------------------------------
\subsection{Observability and Automated Response}
\label{subsec:monitoring}
% ----------------------------------------------------------------

The monitoring layer consists of a \textbf{telemetry subsystem} and an \textbf{alert
manager}. The telemetry subsystem collects metrics from all layers using a pull-based
model \cite{nguyen2022loadbalancing}, spanning all observable infrastructure
categories: physical servers (CPU utilisation, memory consumption, disk I/O
throughput, and energy draw), virtual machines (per-VM CPU steal time and
working-set size), and physical and virtual network devices (port utilisation,
packet loss counters, inter-VM traffic volumes).
% --- NEW: retention and correlation ---
Data is stored with \textbf{time-windowed retention policies} that preserve
high-resolution data for anomalous intervals and apply progressive downsampling to
normal ones. Co-located metrics --- such as the CPU and memory utilisation of all
VMs sharing the same physical host --- are stored with their correlational
relationships preserved, enabling \textbf{correlation-based anomaly detection}
rather than isolated threshold crossings.
% --- END NEW ---

The alert manager maps structured events to actions: scaling requests to the
virtualisation layer, or operator notifications for situations requiring human review.
Grouping and inhibition rules prevent alert storms during cascading failures by
consolidating related events and suppressing symptoms when a root-cause alert is
already active.

\section{Intelligence and Security}
\label{sec:intelligence}
% ================================================================

Static thresholds and manual oversight are insufficient at scale. The architecture
adds three intelligent components --- a conversational assistant, a predictive model,
and a two-agent decision system --- all protected by a zero-trust security design.

% ----------------------------------------------------------------
\subsection{Conversational Administration Assistant}
\label{subsec:assistant}
% ----------------------------------------------------------------

A natural-language assistant is embedded in the cluster management interface,
allowing operators to query cluster state in plain language without navigating
dashboards or memorising CLI syntax. Its autonomy is bounded: read queries execute
immediately, but any write action is suspended until the operator explicitly confirms.
The assistant is also the single human-facing interface through which the predictive
model surfaces recommendations.

% ----------------------------------------------------------------
\subsection{Predictive Resource Management}
\label{subsec:predictive}
% ----------------------------------------------------------------

The predictive model operates across two horizons. \textbf{Before VM creation (H1)},
it recommends an initial resource allocation based on service type, expected load,
and usage patterns of similar running services, reducing early scaling events.
\textbf{At runtime (H2)}, it applies time-series forecasting to detect trajectories
heading toward a scaling threshold and sends pre-emptive recommendations through
the assistant for operator approval.
% --- NEW: dynamic thresholds, adaptive weights, incremental learning ---
The model serves three additional functions.
First, \textbf{dynamic alert thresholds}: rather than relying on the fixed values
in Table~\ref{tab:scaling}, it continuously recalibrates warning and critical
thresholds using recent telemetry as a learned baseline, raising them during
high-traffic events and tightening them during quiet periods to reduce false
positives.
Second, \textbf{adaptive fitness weights}: the model continuously identifies the
current structural bottleneck of the cluster (e.g.\ memory pressure or I/O
saturation) and dynamically adjusts the weights $w_1$--$w_4$ in
Equation~\ref{eq:fitness}, so that subsequent placement decisions automatically
prioritise the constrained resource.
Third, to remain effective as workloads evolve, the model employs
\textbf{incremental self-supervised learning}: at regular intervals it ingests the
latest cluster metrics and updates its internal representations using its own recent
predictions as soft labels, adapting to new baseline behaviours without requiring
external ground-truth datasets.
% --- END NEW ---

% ----------------------------------------------------------------
\subsection{Autonomous Decision-Making and Risk-Based Escalation}
\label{subsec:escalation}
% ----------------------------------------------------------------

Remediation is handled by a \textbf{Planner--Critic} system. The \textbf{Planner}
reads telemetry, bottleneck signals, and action history; when it detects a problem
it proposes a concrete action and assigns an initial risk level. The \textbf{Critic}
independently validates the proposal against three conditions --- host headroom,
absence of runaway loops, and alignment with the predicted bottleneck --- and may
approve, reject, or escalate the risk. A critical constraint: the Critic may
\textit{raise} but is structurally prohibited from \textit{lowering} the Planner's
risk classification, guarding against adversarial misclassification.
% --- NEW: orchestration layer isolation ---
The agents do not hold direct credentials to the infrastructure management
interfaces; they submit structured proposals to an independent \textbf{orchestration
layer} that validates the execution context before dispatching commands --- a
compromised agent can propose but cannot execute unilaterally.
% --- END NEW ---

illustrates the full pipeline.

expired, preventing an adversary from poisoning the queue and waiting for accidental
approval.

reconstruction of the sequence of events leading to any infrastructure state;
(ii)~detection of gradual privilege-escalation patterns that would be invisible in
any single event; and (iii)~permanent accountability for every infrastructure
change, whether autonomous or human-initiated.

% ----------------------------------------------------------------
\subsection{Security Architecture}
\label{subsec:security}
% ----------------------------------------------------------------

Security follows \textit{defence in depth} within a \textit{zero-trust} model:
no entity is trusted by position, every communication is authenticated, and every
component holds the minimum permissions it needs \cite{saxena2022secure}.

\textbf{Network and segmentation.} Hardware firewalls enforce a perimeter allowlist
with bidirectional filtering --- both ingress and egress --- preventing compromised
internal components from establishing unauthorised outbound channels. The
three-segment overlay enforces internal microsegmentation so a compromised workload
cannot move laterally. An anti-DDoS layer absorbs volumetric attacks before they
reach internal services.

\textbf{Identity and integrity.} Every entity holds a cryptographically verifiable
identity; all messages carry a digital signature verified before processing.
Credentials are short-lived and rotated regularly; plaintext channels are prohibited
even on internal segments.

% --- NEW: runtime anomaly detection as dedicated security component ---
\textbf{Runtime anomaly detection.} A dedicated security monitoring agent operates
continuously, subscribing to the same telemetry streams as the alert manager but
applying a behavioural lens oriented toward deviation rather than resource
saturation. It evaluates every observable component against static integrity
baselines and dynamically learned profiles. A \textit{critical} classification
triggers an immediate alert to the administrator, bypassing all aggregation; a
\textit{warning} classification is dispatched at a configured periodic interval,
preserving administrator attention without real-time noise for every minor deviation.
% --- END NEW ---

\textbf{Patch and supply-chain hygiene.} An automated daily process patches every
stack layer from hypervisor to auxiliary services. Components are sourced from
official channels only and verified by signature or content-addressed digest before
installation.

\textbf{Container and VM hardening.} VMs expose only the virtual hardware required;
containers receive only the kernel capabilities they need and filesystems are mounted
read-only wherever possible. Monitoring components hold no provisioning credentials.

\textbf{Cognitive agent security.} The assistant requires administrator authentication
before any query reaches the Planner. Agents submit structured proposals to an
independent orchestration layer that validates execution context before dispatching
commands --- a compromised agent can propose but cannot execute unilaterally. The
Critic's monotonic risk constraint provides a second structural defence.

% ================================================================
\section{Conclusion}
\label{sec:ch2_conclusion}
% ================================================================

The architecture resolves the efficiency--availability tension through intelligent
automation at every layer. The hybrid WOA--DE algorithm minimises resource mismatch
in VM placement; Best Fit scheduling maximises VM utilisation; reactive and predictive
scaling --- augmented by adaptive thresholds and dynamic fitness weights --- keep
capacity matched to demand; the three-segment overlay enforces tenant isolation; and
the Planner--Critic pipeline ensures autonomous actions are proportionate and
auditable. The immutable audit log, digital signatures, TTL-bounded approval queue,
and dedicated security monitoring agent form a coherent defence-in-depth posture
protecting the entire stack. The conversational assistant ties all three intelligent
components into a single human-readable interface that keeps operators in control
without slowing routine operations. Chapter~3 covers the implementation: tool choices,
configuration, and deployment steps.
